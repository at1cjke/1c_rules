# Стандарты разработки на платформе 1С:Предприятие

## 1. Назначение и источник

Практический свод для разработки, доработки и проверки конфигураций 1С. Перед изменением кода прочитать соответствующие разделы этого файла и использовать контрольный список в конце.

Источник: **«Система стандартов и методик разработки конфигураций 14_10_2025.pdf»**, 569 страниц, находится рядом с этим файлом. Дата редакции указана по имени файла; дата подготовки свода — 24.10.2026. Это изложение предоставленного документа, а не проверка актуальности стандартов на сайте 1С.

Ссылки вида **№ 456, с. 167–168** означают идентификатор `std456` в документе и порядковые страницы PDF, считая первую страницу за 1. Тематический указатель в приложении помогает найти подробные требования, исключения и иллюстрации.

### Как применять

- **Обязательно / запрещено** — требование или запрет исходного стандарта.
- **Рекомендуется / следует / как правило** — сохранить рекомендательный характер правила и учитывать описанные в источнике исключения. Числовые ориентиры производительности не превращать в универсальные ограничения.
- Правила применять с учетом области действия: управляемое, мобильное или обычное приложение, библиотека, сервисная модель, конкретная версия платформы и режим совместимости.
- Для частного случая, который не раскрыт в своде, обращаться к соответствующему разделу PDF. Свод не является дословной копией всех 569 страниц; подробности оформления, особенно показанные изображениями, проверять в оригинале.
- Конкретные методы БСП применять, только если соответствующая подсистема и ее API существуют в используемой версии конфигурации. Не создавать вызовы несуществующих библиотечных методов по одному примеру из стандарта.
- Требования проекта и явно согласованные исключения учитывать отдельно. Не выдавать организационные правила проекта за требования этого PDF; при противоречии фиксировать основание выбранного решения.

## 2. Общие требования и совместимость

**Источники:** № 467, с. 5–6; № 785, с. 29; № 680, с. 32–33; № 723, с. 39–40; № 759, с. 48.

1. Использовать штатные документированные возможности платформы.
2. Обеспечивать работу на поддерживаемых конфигурацией СУБД, ОС, в клиентских приложениях и режимах. Не закладывать зависимость от конкретной СУБД или Windows без обоснованного ограничения области применения.
3. Ключевые возможности веб-клиента должны работать без расширения работы с файлами; взаимодействие с пользователем организовывать асинхронно.
4. Конфигурация не должна содержать ошибок проверки конфигурации. Несущественные предупреждения учитывать по отдельному стандарту № 759; не отключать проверки целиком ради устранения предупреждений.
5. Не оставлять неиспользуемые объекты метаданных. Имена, синонимы и тексты должны быть осмысленными и грамотно написанными.
6. Перед использованием нового API определить минимальную версию платформы и режим совместимости. Пример версии в PDF не является указанием обновить любой проект до этой версии.
7. Для Linux и macOS учитывать регистр имен файлов, доступность внешних компонент, особенности путей и отсутствие Windows-специфичных средств. Предпочитать платформенные средства вместо COM и внешних программ.
8. Объекты метаданных верхнего уровня рекомендуется сортировать по имени; подчиненные — по прикладной логике и удобству использования.

## 3. Модель данных и метаданные

**Источники:** № 683, с. 52–56; № 541, с. 57; № 474, с. 58–60; № 478, с. 61; № 473, с. 62–63; № 432, с. 64–65; № 728, с. 66–67; № 477, с. 72; № 632, с. 76; № 697, с. 79–80.

### Выбор объекта

| Задача хранения | Предпочтительный объект |
| --- | --- |
| Условно-постоянные сущности с собственной идентичностью | Справочник |
| Фиксированный список значений без дополнительных реквизитов | Перечисление |
| Одиночная пользовательская настройка общего назначения | Константа |
| Событие предметной области, хозяйственная операция | Документ |
| Процесс и адресованные исполнителям действия | Бизнес-процесс и задача, если доступны в целевой платформе |
| Приход, расход, остатки и обороты показателей | Регистр накопления |
| Сведения, значения по измерениям, история значений | Регистр сведений |
| Учет по принципу двойной записи | План счетов и регистр бухгалтерии |
| Учет начислений и удержаний | План видов расчета и регистр расчета |
| Пользовательский состав характеристик и их типов | План видов характеристик |

Это схема выбора, а не замена анализа сущности и критериев из № 683.

- Не подменять специализированные объекты платформы универсальными таблицами без необходимости.
- Регистр должен быть самодостаточен: отчетам и алгоритмам по регистру не должно требоваться восстанавливать смысл его записей через анализ конкретных видов регистраторов.
- У каждого объекта и подчиненного элемента с соответствующим свойством обязательно заполнить синоним. Для стандартных реквизитов учитывать прикладной смысл; для `Родитель` и `Владелец` задавать прикладные синонимы вместо умолчаний.
- Комментарий к метаданным использовать для пояснения назначения и особенностей, которые не выражены именем и синонимом.
- Коды и номера проектировать как идентификаторы с учетом уникальности, длины, серий и автонумерации; не возлагать на них произвольную бизнес-логику.
- Строки, как правило, должны иметь переменную и обоснованную максимальную длину. Фиксированную длину использовать только при необходимости дополнения пробелами. Не назначать неограниченную длину всем строкам.
- Для составных ссылочных типов задавать только необходимые типы. Избегать «любой ссылки» и избыточного перечня типов: это усложняет запросы и увеличивает число соединений.
- Повторяющиеся определения типов с единым смыслом выносить в определяемые типы, когда это соответствует № 704, с. 22–23.
- Общие реквизиты применять к действительно общим данным объектов, учитывая их влияние на структуру и разделение данных: № 677, с. 21.
- Для устойчивых значений, к которым обращается код, рассмотреть предопределенные элементы. Не подменять их поиском по пользовательскому наименованию.
- Не удалять утратившую актуальность сущность, если на нее должны ссылаться исторические данные. Предусматривать прикладное прекращение использования и ограничение выбора: № 638, с. 77–78.

### Имена метаданных

**Источники:** № 550, с. 7–10; № 474, с. 58–60.

- Слова соединять без пробелов, каждое слово начинать с прописной буквы. Выбирать термины предметной области.
- Не добавлять слова, которые лишь повторяют класс объекта: `Справочник`, `Документ`, `Отчет`, `Обработка`, `Макет`, если они не уточняют смысл.
- Справочники, перечисления, журналы документов, регистры сведений и накопления рекомендуется именовать во множественном числе: `Контрагенты`, `ВидыОпераций`, `КурсыВалют`.
- Документ называть по отражаемому процессу или событию, лаконично и однозначно.
- Отчеты, обработки, константы, формы и макеты именовать по назначению. Название варианта отчета должно само описывать содержание, а не состоять из слов «Основной» или «По заказам» без контекста отчета.
- Команды действий и подписки на события обычно именовать от неопределенной формы глагола. Команды навигации — по открываемым данным.
- Роли называть по разрешенной функции либо должностным обязанностям согласно принятой модели прав.
- Для веб-сервисов, операций и параметров рекомендуется английский язык, понятный внешним системам.

## 4. Архитектура модулей и программный интерфейс

**Источники:** № 469, с. 24–26; № 455, с. 169–175; № 486, с. 222; № 544, с. 223; № 630, с. 391–392.

### Где размещать логику

- **Модуль объекта:** поведение конкретного экземпляра и поддержание его корректного состояния.
- **Модуль менеджера:** операции, для которых не нужен экземпляр объекта. Не получать объект только ради вызова функции, которой он по смыслу не требуется.
- **Общий модуль:** функции подсистемы или механизма, совместное использование кода несколькими объектами.
- **Модуль формы:** логика конкретной формы. Общую бизнес-логику не связывать с ее открытием и элементами интерфейса.
- В модулях команд и общих команд не размещать экспортные процедуры и функции.
- В модулях форм экспорт не использовать как публичный API. Исключение — обработчики оповещений; обмен данными с формой организовывать параметрами, результатом закрытия и оповещениями.

### Контексты общих модулей

| Назначение | Именование | Основное правило |
| --- | --- | --- |
| Внутренняя серверная логика | `РаботаСЗаказами`, при необходимости `...Сервер` | `Вызов сервера` выключен; остальные контексты — по области применения |
| Серверный API для клиента | `РаботаСЗаказамиВызовСервера` | `Сервер` и `Вызов сервера`; только разрешенные клиентские операции |
| Клиентская логика | `РаботаСЗаказамиКлиент` | Клиентские контексты |
| Одинаковый код клиента и сервера | `РаботаСЗаказамиКлиентСервер` | Без удаленного вызова сервера и без разделения логики через `#Если Сервер` |
| Повторно используемые результаты | `...ПовтИсп`, `...КлиентПовтИсп` | Явно выбран срок кеширования |
| Привилегированный модуль | `...ПолныеПрава` | Минимальный обоснованный объем полномочий |
| Переопределяемые точки библиотеки | `...Переопределяемый`, `...КлиентПереопределяемый` | По правилам библиотеки |

Для серверной логики, которая также нужна в обычном приложении и внешнем соединении, учитывать соответствующие признаки из № 469. Не устанавливать всем модулям одинаковый набор флажков автоматически.

### Структура

Общий модуль разделять на области в следующем порядке; пустые ненужные области не создавать:

```bsl
#Область ПрограммныйИнтерфейс
// API для внешних потребителей подсистемы.
#КонецОбласти

#Область СлужебныйПрограммныйИнтерфейс
// Ограниченный круг потребителей согласно архитектуре библиотеки.
#КонецОбласти

#Область СлужебныеПроцедурыИФункции
// Внутренняя реализация.
#КонецОбласти
```

Для модулей объектов и аналогичных модулей соблюдать последовательность: описание переменных, программный интерфейс, обработчики событий, служебный программный интерфейс, служебные процедуры и функции, инициализация. Применять только разделы, допустимые для данного вида модуля.

В форме выделять обработчики событий формы, элементов шапки, каждой таблицы, команд и служебную реализацию. Детальный шаблон — № 455.

## 5. Оформление и качество кода

**Источники:** № 456, с. 167–168; № 647, с. 176–177; № 454, с. 186; № 441, с. 188–189; № 444, с. 190–191; № 440, с. 192–193; № 439, с. 194–195; № 442, с. 196; № 445, с. 197; № 547, с. 214.

1. Тексты модулей писать на русском языке. Исключения — внешние интерфейсы, идентификаторы сторонних систем и другие случаи исходного стандарта.
2. В текстах модулей не использовать `ё`, неразрывные пробелы и типографские варианты минуса. Для пользовательских текстов действуют отдельные правила № 598.
3. Для синтаксического отступа использовать **табуляцию шириной 4 символа**. Пробелы допустимы для выравнивания продолжений выражений.
4. Придерживаться одного оператора на строку. Исключение исходного стандарта — однотипные присваивания; ради читаемости обычно оставлять их отдельными строками.
5. Рекомендуемая длина строки — **до 120 символов** с учетом ширины табуляции. Переносить выражения; не портить пользовательский текст искусственными переводами строки.
6. При переносе логического выражения ставить `И`, `ИЛИ` в начале следующей строки. Аналогично оформлять арифметические выражения и конкатенацию по № 444.
7. Между `//` и комментарием ставить пробел. Большие пояснения помещать перед кодом, короткие допустимы в конце строки. Пояснять причины и неочевидные ограничения.
8. После завершения разработки не оставлять неиспользуемые методы, отладочный код, закомментированные фрагменты, `TODO`, отметки слияния и персональные служебные записи. Отдельные согласованные правила маркировки доработок проекта учитывать как проектное исключение.
9. Имена переменных и методов должны раскрывать назначение. Не начинать переменные с подчеркивания и не использовать односимвольные имена.
10. Процедуры обычно именовать действием: `ЗаполнитьТовары`. Функции — по возвращаемому результату: `ПараметрыЗаполнения`, `ЕстьОшибки`; если основной смысл — действие, допустим глагол. Булевы переменные называть по истинному состоянию: `ЕстьОшибки`, `ЭтоНовыйОбъект`.
11. Булевы значения не сравнивать с литералами `Истина` и `Ложь`: писать `Если ЕстьОшибки Тогда` и `Если Не ЕстьОшибки Тогда`.
12. Использовать системные наборы значений: например, `Символы.ПС`, а не числовой код символа.
13. Тип проверять сравнением `ТипЗнч(Значение)` с `Тип("...")`, а не по строковому представлению типа.
14. Если объект или ссылка уже есть, метаданные получать через его метод `Метаданные()`. Для поиска по неизвестному заранее типу применять `Метаданные.НайтиПоТипу(...)`.
15. Избегать дублирования общей логики; не объединять искусственно реализации, которые по назначению должны развиваться независимо.
16. Директивы `&НаКлиенте`, `&НаСервере`, `&НаСервереБезКонтекста` применять в модулях управляемых форм и команд. В других модулях учитывать их контекст и правила препроцессора.
17. Не разветвлять клиент-серверный общий модуль через `#Если Клиент` / `#Если Сервер`; различающуюся логику выносить в соответствующие модули.
18. Оператор `Перейти` не рекомендуется; в клиентском коде управляемых форм, модулей команд и соответствующих общих модулей запрещен из-за веб-клиента.

## 6. Параметры, описания методов, коллекции и состояние

**Источники:** № 453, с. 178–181; № 640, с. 182–183; № 641, с. 184–185; № 639, с. 199–201; № 494, с. 202; № 452, с. 215–216; № 693, с. 227–228; № 781, с. 229; № 782, с. 230.

- Методы программного интерфейса обязательно документировать: назначение, параметры с типами, возвращаемое значение; при необходимости ограничения и пример. Описание писать перед директивой компиляции.
- Для массивов указывать тип элементов. Для структур и таблиц описывать свойства и колонки либо ссылаться на функцию-конструктор, которая определяет их состав.
- Передавать зависимости параметрами, не заменять параметры скрытым использованием переменных модуля и реквизитов формы.
- Параметры располагать логически, от общего к частному; необязательные — после обязательных. Рекомендуемый ориентир — не более **7** параметров.
- Для сложного набора параметров использовать функцию-конструктор структуры или типизированной таблицы. Определять все допустимые свойства и значения по умолчанию в одном месте; вызывающая сторона заполняет предусмотренные свойства, а не расширяет контракт произвольно.
- В конструктор `Новый Структура(...)` рекомендуется передавать не более **3** значений свойств. Для остальных применять `Вставить` и явные присваивания. Не усложнять вызов вложенными конструкторами.
- Не использовать переменные модуля как универсальное хранилище состояния и кеш. Между обработчиками объекта при необходимости передавать служебные данные через `ДополнительныеСвойства`.
- Параметры сеанса инициализировать в модуле сеанса, преимущественно по требованию. Не использовать их как произвольное хранилище: № 413, с. 18–19.
- Персональные настройки хранить штатными средствами хранилища настроек: № 557, с. 27–28.
- Для повторных поисков по большой таблице значений рассмотреть подходящие индексы с хорошей селективностью; ориентир исходного стандарта — от 1000 строк, с учетом частоты поиска.
- При сортировке таблиц по ссылкам учитывать обращения за представлениями. Для сортировки по имени заранее получить представления, для технической сортировки использовать подходящий способ сравнения ссылок.
- При массовой конкатенации, ориентировочно от 1000 операций, применять `СтрСоединить` и при необходимости `СтрРазделить`; обычную короткую конкатенацию сохранять читаемой.

## 7. Объекты, документы и обработчики событий

**Источники:** № 603, с. 68–70; № 633, с. 71; № 464–466, с. 81–84; № 463, с. 85–87; № 396, с. 88–89; № 773, с. 91; № 687, с. 187; № 450, с. 219; № 451, с. 221.

### Обработчики

| Обработчик | Назначение и ограничения |
| --- | --- |
| `ОбработкаЗаполнения` | Специальное заполнение по типу основания, затем заполнение оставшихся значений по умолчанию; ограничения ввода на основании проверять здесь |
| `ОбработкаПроверкиЗаполнения` | Внетранзакционные проверки заполнения; корректировать `ПроверяемыеРеквизиты`, не дублировать стандартные проверки |
| `ПередЗаписью` | Подготовка значений объекта и необходимые проверки перед записью |
| `ПриЗаписи` | Изменение связанных данных после записи объекта; запрещено менять содержимое уже записанного объекта |
| `ПередУдалением` | Действия перед удалением с учетом обмена и ссылочной целостности |
| `ПриКопировании` | Очистка и переопределение значений, которые не должны переходить в копию |
| `ОбработкаПроведения` | Формирование движений и проверки учетных инвариантов в транзакции проведения |

- Не присваивать параметру `Отказ` значение `Ложь`: можно отменить отказ, установленный ранее другим обработчиком. При обнаружении нарушения устанавливать только `Истина`.
- `ОбработкаПроверкиЗаполнения` не вызывается автоматически при любой программной записи. Если сценарий требует проверки, вызывающий код должен явно организовать ее.
- Проверки, необходимые для целостности данных, размещать в транзакционных обработчиках. Внетранзакционная проверка формы не защищает от конкурентного изменения данных.
- Для обычных исправимых пользователем ошибок в обработчиках с параметром `Отказ` накапливать сообщения и устанавливать отказ, а не прерывать первую проверку исключением. Для ограничений ввода на основании в `ОбработкаЗаполнения` стандарт предусматривает исключения.
- При программном создании прикладных объектов использовать методы менеджеров: `СоздатьЭлемент`, `СоздатьДокумент`, `СоздатьНаборЗаписей`. Для объектов, имеющих такие менеджеры, не использовать конструктор `Новый`.
- При создании объекта программно явно вызывать `Заполнить(...)` согласно сценарию, чтобы отработала штатная логика заполнения.

### ОбменДанными.Загрузка

В `ПередЗаписью`, `ПриЗаписи`, `ПередУдалением` и подписках на эти события действия выполнять после проверки:

```bsl
Если ОбменДанными.Загрузка Тогда
	Возврат;
КонецЕсли;
```

Исключения, например регистрация данных к выгрузке на другие узлы, рассматривать по № 773 и пояснять в коде. Вызывающая сторона, установившая `ОбменДанными.Загрузка = Истина`, отвечает за целостность загружаемых данных. Не применять этот флаг как универсальный способ обходить проверки при обычной записи.

### Проведение

- Проведение означает отражение события в учете, непроведенный документ — черновик. Не отключать проведение ради выполнения записи и учета за одно действие: записывать в режиме проведения.
- Непроведенные и помеченные на удаление документы не должны иметь активных движений.
- Статусы документа уточняют этап жизненного цикла, но не подменяют сам факт проведения.
- Как правило, движения записывает платформа после завершения обработчика. Явную запись в обработчике использовать только при обоснованной необходимости, например для последующей проверки остатков.
- Порядок записи регистров согласовывать для всех документов, чтобы уменьшать риск взаимоблокировок.
- Повторное проведение при неизменных значимых данных должно сохранять ожидаемый учетный результат; изменения алгоритмов сопровождать обработчиками обновления либо поддержкой прежней логики для исторических документов.

## 8. Запросы: оформление и корректность

**Источники:** № 437, с. 100–103; № 436, с. 104–105; № 438, с. 106; № 435, с. 107–108; № 434, с. 109; № 412, с. 110–111; № 535, с. 112–113; № 726, с. 114–115; № 758, с. 116; № 787, с. 117.

1. Текст запроса структурировать, в том числе короткий. Ключевые слова языка запросов писать в принятом стандартом верхнем регистре; поля и источники именовать осмысленно.
2. Явно назначать понятные псевдонимы. Перед псевдонимом поля обязательно указывать `КАК`. Избегать односимвольных псевдонимов и начала с подчеркивания.
3. Значения передавать через параметры, особенно пользовательские данные, даты, ссылки и локализуемые строки. Не собирать литералы запроса конкатенацией значений.
4. Не использовать закомментированные части запроса как механизм его модификации. При необходимости изменения структуры соблюдать № 437 и сохранять возможность разбора конструктором.
5. Не выполнять однотипный запрос для каждого элемента: получать данные сразу для набора значений, использовать пакет запросов или `ОБЪЕДИНИТЬ ВСЕ`.
6. Для проверки пустоты результата применять `РезультатЗапроса.Пустой()`, а не выгрузку результата ради подсчета строк.
7. Обычно применять `ОБЪЕДИНИТЬ ВСЕ`. `ОБЪЕДИНИТЬ` использовать, только когда действительно требуется удаление дубликатов.
8. `ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ` в общем случае не рекомендуется. Его сочетание с обращением к табличным частям в разделе выборки не допускается по № 435.
9. Если порядок влияет на алгоритм или результат отображается пользователю, задавать `УПОРЯДОЧИТЬ ПО`. В остальных случаях не добавлять сортировку без необходимости. Учитывать различия порядка `NULL` на разных СУБД.
10. Для пользовательской сортировки ссылок использовать понятные пользователю представления. `ПЕРВЫЕ` совместно с `АВТОУПОРЯДОЧИВАНИЕ` запрещено; само автоупорядочивание в остальных случаях также не рекомендуется.
11. Для количества записей использовать `КОЛИЧЕСТВО`, а не `СУММА(1)`. В особом случае условного подсчета через сумму обеспечить достаточную разрядность.
12. Для деления, среднего и умножения дробных чисел при необходимости явно задавать разрядность и точность через `ВЫРАЗИТЬ(... КАК ЧИСЛО(...))`, чтобы результаты совпадали на поддерживаемых СУБД.
13. Для `ПОДОБНО` использовать строковый литерал или параметр. Шаблон вычислять до выполнения запроса, учитывать специальные символы и переносимость на СУБД; не подставлять произвольный пользовательский текст как готовый шаблон.

```bsl
Запрос = Новый Запрос;
Запрос.Текст =
	"ВЫБРАТЬ
	| Контрагенты.Ссылка КАК Ссылка,
	| Контрагенты.Наименование КАК Наименование
	|ИЗ
	| Справочник.Контрагенты КАК Контрагенты
	|ГДЕ
	| Контрагенты.Ссылка В (&Контрагенты)
	|УПОРЯДОЧИТЬ ПО
	| Наименование";
Запрос.УстановитьПараметр("Контрагенты", СсылкиКонтрагентов);
РезультатЗапроса = Запрос.Выполнить();
```

Пример показывает оформление; наличие справочника и состав реквизитов определяются проектом.

## 9. Производительность запросов и чтение данных

**Источники:** № 729, с. 118; № 652, с. 119; № 654–658, с. 120–131; № 708, с. 132–133; № 733, с. 134; № 777, с. 135; № 791, с. 136; № 496, с. 148; № 447, с. 217.

- Выбирать только необходимые поля и строки; не использовать `ВЫБРАТЬ *` «на всякий случай». Агрегацию, отбор и вычисления по возможности выполнять в СУБД.
- Проверять соответствие основных условий отбора и соединений индексам, включая порядок полей составного индекса. Не добавлять индекс на каждое условие механически: учитывать штатные индексы и затраты на запись.
- В основных индексируемых условиях избегать функций и арифметики над полем, отрицаний и неравенств, мешающих поиску по индексу. Преобразовывать условия с сохранением смысла.
- Отборы виртуальных таблиц по возможности передавать в их параметры; ограничивать набор данных как можно раньше. Для `СрезПоследних` и подобных таблиц отдельно проверять, не меняет ли перенос условия смысл результата.
- Не создавать тяжелые соединения с вложенными запросами и виртуальными таблицами. Предпочитать промежуточные временные таблицы; исключение для подзапросов с малым числом записей учитывать по № 655.
- Не использовать подзапросы в условиях соединения. Избегать вложенных соединений, которые создают неявные подзапросы; при переписывании обязательно сохранять семантику.
- При разыменовании составной ссылки ограничивать тип через `ВЫРАЗИТЬ`, если известен нужный вид объекта. Не допускать неявного соединения со всеми возможными типами ради одного поля.
- Временные таблицы должны содержать только нужные поля и строки. Не создавать и удалять одинаковые таблицы в цикле, если их можно подготовить один раз. Большие объемы обрабатывать порциями.
- Разрешать итоги периодических регистров сведений только при подходящих объемах и характере запросов. Разделение итогов регистров накопления и бухгалтерии выбирать с учетом параллельности записи: № 663–664, с. 160–164.
- Дополнительные индексы применять по № 791 для соответствующих сценариев крупных предприятий и лицензий КОРП; тестировать работу с ними и без них. Не делать их единственным условием приемлемой работы на небольших данных.
- Для нескольких реквизитов объекта читать данные запросом или подходящим методом БСП. `ПолучитьОбъект()` и разыменование ссылки могут загрузить объект целиком с табличными частями.
- Чтение регистра сведений без изменения выполнять запросом. Менеджер записи использовать при отборе одновременно по всем измерениям; для других сценариев изменения — набор записей.

## 10. Транзакции, блокировки и ответственное чтение

**Источники:** № 783, с. 137–141; № 460, с. 142; № 490, с. 143–144; № 648, с. 145–147; № 659, с. 157; № 661, с. 165–166.

### Транзакции

- Объединять в транзакцию только действия, которые должны выполняться атомарно. Не охватывать общей транзакцией независимые операции без причины.
- `НачатьТранзакцию()` вызывать непосредственно перед `Попытка`, за пределами ее блока.
- Все дальнейшие действия, включая блокировку, чтение и запись, выполнять внутри одной `Попытка`.
- `ЗафиксироватьТранзакцию()` — последнее действие в блоке `Попытка`.
- В `Исключение` сначала выполнять `ОтменитьТранзакцию()`, затем диагностику и другие действия. При передаче ошибки вверх сохранять ее через `ВызватьИсключение;`.
- Платформа не предоставляет независимых вложенных транзакций. Вложенные вызовы начала/завершения транзакции не являются точками сохранения; перехваченное исключение не означает, что внешнюю транзакцию можно успешно зафиксировать.
- Транзакции делать короткими. Подготовку и тяжелые расчеты по возможности выполнять заранее; проверки целостности и ответственное чтение оставлять под защитой транзакции.
- Не обращаться внутри транзакции к сетевым каталогам, сайтам, почте, FTP, HTTP и другим внешним ресурсам.
- Отключение итогов регистра, запись и обратное включение с пересчетом выполнять атомарно по № 783.

Шаблон управления транзакцией; прикладной код и блокировки подставляются по задаче:

```bsl
НачатьТранзакцию();
Попытка
	// Установить необходимые управляемые блокировки до чтения.
	// Прочитать данные и выполнить связанные изменения.
	ЗафиксироватьТранзакцию();
Исключение
	ОтменитьТранзакцию();
	ВызватьИсключение;
КонецПопытки;
```

### Ответственное чтение

Ответственное чтение — чтение, на основании которого принимаются решения или изменяются данные. Выполнять его в транзакции с предварительной управляемой блокировкой:

- если прочитанные данные затем изменяются — исключительная блокировка до чтения;
- если данные используются для формирования других данных — разделяемая блокировка на читаемые данные и исключительная на изменяемые.

В управляемом режиме блокировок конструкцию `ДЛЯ ИЗМЕНЕНИЯ` не применять. Блокировать минимально необходимый набор записей; соблюдать согласованный порядок блокировок и записи во всех алгоритмах.

Блокировка объекта для редактирования и управляемая транзакционная блокировка решают разные задачи. Первая предотвращает конкурирующее получение такой же блокировки редактирования, но сама по себе не запрещает всем сеансам записать объект. При программном редактировании существующего объекта предусматривать объектную блокировку и учитывать исключения № 490; защиту ответственного чтения проектировать отдельно.

## 11. Массовая запись регистров

**Источник:** № 792, с. 150–156.

- Не рекомендуется записывать регистр в цикле наборами по одной или нескольким записям. Предпочитать порции; типичный ориентир — **1000 записей**, корректировать по измерениям и ограничениям задачи.
- Если в большом наборе изменяется не более **30%** записей, рекомендуется вычислять и записывать изменения вместо полной перезаписи набора.
- Выбирать режимы замещения `Слияние`, `Удаление`, `Обновление` и другие только с учетом поддерживаемой версии платформы, типа регистра, подчиненности регистратору и семантики режима. Конкретный алгоритм брать из № 792.
- Не переносить алгоритм записи независимого регистра механически на движения документа. Учитывать ключи, регистратор и `НомерСтроки`.
- Проверять отбор набора перед записью: замещение по неверному или пустому отбору может изменить существенно больше данных, чем требуется.
- Совмещать пакетную запись с транзакциями, ответственным чтением и блокировками, если изменения вычисляются по ранее прочитанному состоянию.

## 12. Клиент-серверное взаимодействие и длительные операции

**Источники:** № 487, с. 235–242; № 629, с. 243; № 636, с. 400–402; № 628, с. 403; № 642, с. 379–382; № 755, с. 383.

- Контролировать явные и неявные серверные вызовы на пользовательское действие. Объединять необходимые вычисления в один осмысленный вызов, избегать запросов к серверу в цикле.
- При открытии формы готовить нужные данные в `ПриСозданииНаСервере`. Не выполнять дополнительные обращения к серверу из `ПриОткрытии` и `ПриПовторномОткрытии`.
- Если контекст формы не нужен, применять `&НаСервереБезКонтекста` с минимальным набором параметров. Не передавать всю форму или таблицу ради одного значения.
- Контекстный вызов оправдан, если нужна работа с формой и платформенная передача измененных частей коллекций заметно сокращает трафик. Не заменять все вызовы внеконтекстными автоматически.
- Учитывать запреты контекстных вызовов из отдельных клиентских событий. Для записи использовать соответствующие серверные обработчики формы, а не дополнительные обращения из клиентских `ПередЗаписью` / `ПослеЗаписи`.
- Удаленно вызываемые параметры рекомендуется объявлять с `Знач`, чтобы не передавать измененные параметры обратно без необходимости. Результат возвращать функцией.
- На клиенте оставлять интерфейсную и простую быструю логику; ресурсоемкие вычисления выполнять на сервере.
- Большие данные подбора передавать через временное хранилище. Явно управлять сроком жизни данных и удалять их после использования.
- Для `ДанныеФормыКоллекция` учитывать порционную загрузку. При потенциально большом количестве строк, ориентир — от **20**, обход и `НайтиСтроки` выполнять на сервере.
- В часто вызываемых событиях, включая активизацию строки, не инициировать тяжелое обновление немедленно; применять предусмотренный стандартом отложенный однократный обработчик и устранять лишние вызовы.
- Серверные операции, которые в обычном сценарии могут длиться **более 8 секунд**, выполнять асинхронно с использованием фонового задания и получением результата. При наличии БСП использовать механизм длительных операций ее версии.
- Для длительных клиентских операций обеспечивать отзывчивость, показ состояния и возможность прерывания там, где это предусмотрено сценарием. Не заменять асинхронность циклом ожидания на клиенте.

## 13. Кеширование и память

**Источники:** № 724, с. 231–232; № 459, с. 233; № 443, с. 234; № 725, с. 251–253.

- Повторное использование результатов применять для часто востребованных, достаточно дорогих вычислений с ограниченным множеством параметров.
- Выбирать срок кеширования с учетом допустимой актуальности данных. Не рассчитывать, что кеш хранит результат постоянно.
- Не изменять возвращенный кешированный объект. Предпочитать неизменяемые результаты либо создавать отдельную копию для изменения.
- Внутренний вызов функции в том же модуле не обязательно использует кеш; для этого учитывать квалифицированное обращение через имя модуля по № 724.
- Не создавать дополнительный клиентский кеш предопределенных значений без необходимости.
- Не выгружать всю таблицу или результат запроса в память, если достаточно выборки или обработки порциями.
- Ограничивать размер структур, таблиц, временных данных и кешей. Избегать циклических ссылок; учитывать суммарное потребление памяти многими сеансами.

## 14. Безопасность, права и привилегированный режим

**Источники:** № 678, с. 256–257; № 679, с. 258; № 740, с. 259–260; № 669, с. 261–263; № 770, с. 264–265; № 774–775, с. 266–269; № 689, с. 270–274; № 488, с. 275–278; № 532, с. 279; № 737, с. 280–281; № 485, с. 282–284; № 415, с. 285.

### Серверный API

- Любой доступный с клиента серверный метод считать самостоятельной точкой входа. Проверять параметры и полномочия на сервере; скрытие кнопки в форме не является защитой операции.
- Не выставлять `Вызов сервера` всем серверным общим модулям. Открывать только действительно необходимые клиентские операции.
- Передавать клиенту только разрешенные данные и нужный результат. Не возвращать конфиденциальные промежуточные данные вычислений.
- Не принимать от клиента произвольный исполняемый текст и не выполнять его с повышенными правами.

### Роли и доступ

- Права задавать ролями по функциям, предусмотренным конфигурацией. Придерживаться модели элементарных функций и разделения чтения/изменения по № 689.
- Проверять право через `ПравоДоступа` либо предусмотренный механизм проверки. Проверку наличия роли применять в оговоренных случаях, когда проверка конкретного права неинформативна; при БСП учитывать `Пользователи.РолиДоступны`.
- Флажок установки прав для новых объектов должен быть установлен только у `ПолныеПрава`. При добавлении метаданных явно проверять права остальных ролей и права на поля.
- Не предоставлять обычным прикладным ролям интерактивное удаление ссылочных объектов. Удаление помеченных объектов проектировать отдельной контролируемой операцией.
- Не использовать режим технического специалиста как обязательный интерфейс обычной работы.
- При наличии RLS проверять не только доступность формы, но и корректность запросов, записей и отчетов под ограниченными правами.
- `ВЫБРАТЬ РАЗРЕШЕННЫЕ` не использовать для молчаливого отбрасывания данных, необходимых бизнес-логике. Операция должна получить полный необходимый набор либо завершиться отказом в доступе. Для подходящих пользовательских выборок применение допустимо по № 415.

### Привилегированный режим

- Применять локально, когда отключение проверки прав логически обосновано; не превращать его в универсальное исправление ошибок доступа.
- До выполнения привилегированной операции проверить право на саму прикладную функцию, кроме функций, действительно разрешенных всем категориям пользователей.
- Не допускать выдачу через привилегированный метод данных, которые пользователь не вправе получать.
- Контролировать границы и восстановление режима при ошибках согласно конкретному способу его включения.

### Пароли и внешний код

- По возможности запрашивать пароль для операции без сохранения. Если хранение необходимо, использовать специализированный механизм защищенного хранения; при наличии БСП — ее безопасное хранилище.
- Сохраненный пароль не передавать обратно в клиентскую форму для отображения маски. Использовать предусмотренный стандартом маркер наличия сохраненного пароля.
- Не записывать секреты в сообщения, журнал и промежуточные данные.
- Внешний код на сервере по умолчанию должен выполняться в безопасном режиме. Исключения требуют отдельной предусмотренной стандартом процедуры аудита и разрешения администратором; не отключать защиту глобально.
- Перед `Выполнить` / `Вычислить` с внешним или сконструированным по параметрам кодом обеспечить безопасный режим, включая разделение данных для сервиса.
- Для HTTPS/FTPS учитывать проверку сертификатов и доверенные центры сертификации ОС по с. 261–263.
- Внешние компоненты хранить в предназначенных для них макетах и подключать штатными средствами БСП, если она используется.
- Установку компонент и расширений выполнять интерактивно с объяснением назначения пользователю: № 700, с. 426–427.
- Запуск приложений и формирование команд выполнять через предусмотренные безопасные API. Динамическое формирование исполняемых файлов не рекомендуется; журнал изменений на с. 1 формулирует это строже, поэтому при необходимости сверяться с полным № 774.
- Перед программным открытием документов Office запрещать автоматическое выполнение макросов. Особые разрешения и настройки безопасности проектировать по № 775.

## 15. Исключения, диагностика и сообщения

**Источники:** № 498, с. 203–204; № 499, с. 205–207; № 790, с. 208–213; № 400, с. 422–424; № 418, с. 425; № 585, с. 436–439.

### Исключения

- По умолчанию не перехватывать исключение: платформа обеспечивает сообщение, регистрацию и предусмотренную отправку отчета.
- Перехватывать локально вокруг конкретной ожидаемо проблемной операции, когда есть содержательное восстановление, преобразование сообщения, освобождение ресурсов либо продолжение независимой обработки.
- Не оставлять пустой `Исключение` и не скрывать неизвестную ошибку возвратом фиктивного успешного результата.
- Если исключение перехвачено и не передается платформе, обеспечить необходимую диагностику и регистрацию причины; не дублировать без необходимости автоматическую запись при повторной передаче исключения.
- Для бизнес-логики анализировать стабильный строковый код или категорию ошибки, а не локализованный текст. Для новых возможностей `ВызватьИсключение(...)` проверять версию платформы.
- Разделять понятный пользователю текст и подробности для администратора. При преобразовании сохранять исходную причину.
- Для ошибок программного контракта использовать подходящую категорию, например `ОшибкаКонфигурации`; для нарушений прав — штатную проверку прав или соответствующую категорию по № 790.
- Исправимые нарушения заполнения в обработчиках с `Отказ` выводить сообщениями; исключение использовать, когда продолжение проверок бессмысленно либо сценарий явно этого требует.

### Журнал регистрации

- Одна запись соответствует одному событию. Заполнять осмысленный вид события, уровень, объект метаданных, данные и комментарий, когда они применимы.
- Подробности исключения получать через предусмотренное представление ошибки; при БСП использовать `ОбработкаОшибок.ПодробноеПредставлениеОшибки(...)`.
- Не помещать в комментарии неограниченные объемы данных; ориентир стандарта — максимум **10 КБ**.
- Для высокочастотной прикладной выборки истории использовать предназначенный регистр или специализированный механизм, а не журнал регистрации.

### Пользовательские сообщения

- Для сообщений применять `СообщениеПользователю`, а не глобальный `Сообщить`. При БСП — подходящий метод `СообщитьПользователю`.
- Ошибки заполнения связывать с конкретным объектом и полем, где это возможно; показывать весь набор исправимых нарушений.
- Текст должен объяснять проблему и необходимое действие пользователя, без стека и технических подробностей.
- Не уведомлять об очевидном успехе, который уже виден по изменению формы. Подтверждения и предупреждения использовать по назначению, с учетом асинхронного интерфейса.

## 16. Файлы, внешние ресурсы и обмены

**Источники:** № 542, с. 244–250; № 748, с. 254–255; № 637, с. 287; № 701, с. 288–289; № 771, с. 290–291.

- Различать файловые системы клиента и сервера; учитывать права учетной записи ОС, под которой работает соответствующий процесс.
- Запрещена запись в каталог исполняемых файлов платформы, получаемый через `КаталогПрограммы()`.
- Для временных имен использовать платформенные методы, уникальность и штатные каталоги. В веб-клиенте учитывать ограничения доступности методов.
- Удалять временные файлы после использования, включая ошибочные ветки. Не удалять чужие данные по общей маске каталога.
- Явно выбирать кодировку для переносимых текстовых файлов, когда API позволяет это сделать; учитывать имена файлов и особенности разных ОС.
- Для взаимодействия с файловой системой веб-клиента применять асинхронные платформенные методы или API БСП соответствующей версии.
- При HTTP, FTP, почте и веб-сервисах задавать конечные таймауты. Длительную обработку внешнего сервиса проектировать как запуск, проверку готовности и получение результата, если простое ожидание неприемлемо.
- Регистрацию изменений в планах обмена с отборами строить с учетом предыдущего и нового состояния объекта, удаления и взаимосвязанных таблиц; учитывать передачу данных, уже полученных по обмену.
- Для обменов между конфигурациями на БСП применять EnterpriseData в области действия № 771. Переход на другую конфигурацию и регулярная синхронизация — разные сценарии; исключения для иных механизмов брать из стандарта.
- Не менять правила сопоставления классификаторов произвольно: учитывать уникальные идентификаторы и предусмотренный порядок сопоставления по № 637.

## 17. Формы, списки и командный интерфейс

**Источники:** № 727, с. 345; № 722, с. 350–356; № 711–721, с. 358–374; № 404, с. 388–389; № 741, с. 390; № 630, с. 391–392; № 742, с. 393; № 703, с. 394; № 489, с. 409–410; № 495, с. 411; № 558, с. 413–414; № 702, с. 415; № 732, с. 416–418.

### Поведение

- Формы открывать через `ОткрытьФорму`, параметры передавать при открытии. Не получать форму и затем менять ее публичные реквизиты как способ передачи параметров.
- Результат выбора или диалога возвращать через закрытие формы и обработчик оповещения, не через вызовы экспортных методов формы-владельца.
- Не открывать другую форму из `ПриОткрытии`, если это нарушает порядок открытия и активизацию окон.
- Не использовать модальные окна и синхронные вызовы в области действия № 703. Выбирать асинхронные методы, доступные целевой версии платформы.
- Блокирующее или независимое открытие выбирать по сценарию, не подменять блокировку владельца модальностью.
- Для команд, которые могут изменить объект, устанавливать признак `ИзменяетДанные`: № 537, с. 399.
- Бизнес-ограничения реализовывать в данных и объектной логике; недоступность поля формы сама по себе не защищает данные.
- Не рассчитывать на наличие автоматически создаваемых или пользовательских элементов формы без проверки правил № 536 и № 545, с. 397–398.

### Динамические списки

- Делать запросы простыми и быстрыми, выбирать основную таблицу и режим чтения осознанно; динамическое считывание обычно предпочтительно.
- Для заведомо больших списков не использовать режим без основной таблицы, который накапливает все прочитанные данные в буфере.
- Сложное вычисляемое состояние при необходимости хранить и поддерживать отдельно, а не пересчитывать тяжелым запросом при каждом отображении списка.
- Ограничивать соединения, подзапросы, группировки и другие тяжелые конструкции по № 732; учитывать, что платформа дополняет запрос сортировкой, поиском и отборами.
- Для объектов ссылочных типов рекомендуется включать поле `Ссылка`, скрыв пользовательскую видимость. Для полей, необходимых алгоритмам независимо от видимости колонок, обоснованно устанавливать `Использовать всегда`.
- Команды должны корректно работать с группировками и отсутствием текущей строки. Не принимать строку группировки за ссылку объекта.
- После изменений из нестандартных команд предусматривать обновление нужных списков через штатные оповещения; фильтровать имена событий, не обновлять все формы на любое оповещение.
- Условное оформление не использовать для скрытия строк целиком; строки исключать отбором: № 710, с. 404–405.

### Компоновка и тексты

- Проектировать формы под типовое разрешение **1280×768**, учитывая область применения стандарта. Не переносить размеры обычного приложения на управляемые формы.
- Группировать поля по задачам пользователя, важные и обязательные поля располагать на первоначально доступной странице. Не перегружать форму вкладками и второстепенными командами.
- В пределах формы одинаково располагать заголовки однострочных полей. Для шрифтов и цветов использовать стили и штатные состояния оформления, а не произвольные абсолютные значения.
- Командный интерфейс строить по областям деятельности, а не по техническим видам метаданных.
- Кнопку по умолчанию размещать первой слева; порядок однотипных команд делать одинаковым. «Отмена» должна действительно отменять действие и закрывать форму, не быть кнопкой по умолчанию.
- Подпись флажка располагать справа. Для единиц измерения учитывать отдельные правила поля ввода и колонки списка: № 593, с. 526–528.
- Подсказки давать там, где они поясняют неочевидное поведение, а не повторяют заголовок. Пользовательские тексты писать языком предметной области.
- Не переназначать зарезервированные сочетания клавиш: № 430, с. 377–378.
- При разработке новых форм сверять конкретную компоновку с иллюстрациями и специальными стандартами указателя.

### Обычное приложение

Стандарты с. 539–569 относятся к обычному приложению. Применять их только при работе с ним: состав интерфейсов, привязки, размеры кнопок, закладки, подсказки, порядок обхода и другие ограничения отличаются от управляемых форм. Например, для чтения значений строки табличного поля не использовать его `ТекущаяСтрока`, а обращаться к данным строки по № 523, с. 566.

## 18. Отчеты, СКД и печатные формы

**Источники:** № 407, с. 226; № 548, с. 384–385; № 789, с. 386–387; № 449, с. 220; № 670–676, с. 457–473; № 645, с. 535.

- Выбирать средства отчета с учетом проекта. PDF содержит требования как к отчетам на СКД, так и к другим отчетам; сам по себе он не устанавливает безусловное правило «все отчеты только на СКД».
- В СКД отделять обязательные параметры выполнения от необязательных пользовательских отборов. Для отборов использовать средства СКД, не заставляя пользователя заполнять лишние параметры.
- Варианты отчета должны соответствовать самостоятельным задачам анализа. В заголовке отражать цель, содержание и важные настройки; избегать неинформативных названий.
- Настройки периода, группировок, отборов, показателей и расшифровок делать понятными пользователю. Выводить единицы измерения и выбирать оправданную сортировку.
- Диаграмму использовать, если она помогает сравнению или анализу, а не как украшение. Таблицы и списки проверять на читаемость и пригодность к печати.
- Для табличного документа заранее получать представления ссылок. Не передавать сами ссылки в параметры ячеек, вызывая множество обращений за представлениями.
- Печатные формы разрабатывать с учетом изменений макета пользователем: не привязывать алгоритм без необходимости к координатам и фиксированному числу строк, использовать именованные области и параметры по № 789.
- Проверять длинные строки, переносы, разбиение на страницы, формат бумаги и вывод числовых значений. Наименование команды печати должно соответствовать печатной форме.

## 19. Локализация, время и денежные значения

**Источники:** № 643, с. 11–13; № 458, с. 317; № 769, с. 318–321; № 761–767, с. 322–341; № 778, с. 342–343; № 784, с. 344.

- Пользовательские строки в коде обязательно оформлять через `НСтр`. Не собирать переводимое предложение из отдельных слов; использовать цельный шаблон и подстановки, например `СтрШаблон`.
- Не локализовать технические строковые идентификаторы, имена реквизитов, коды ошибок и ключи протоколов. Не сравнивать данные алгоритма с переведенными представлениями.
- Строки, выводимые запросом и СКД пользователю, передавать параметрами с локализованными значениями либо применять предусмотренные способы локализации выражений.
- Даты и числа отображать с учетом локали; для обмена использовать стабильное машинное представление, а не пользовательское форматирование.
- Для таблиц и групп формы задавать осмысленные заголовки даже при скрытом показе заголовка. Заголовки вычисляемых колонок динамического списка определять явно, где это требуется стандартом.
- Автоматически создаваемые строки, которые сохраняются как данные ИБ и показываются разным пользователям, формировать на языке информационной базы, а не на языке текущего пользователя.
- Национальную специфику международного решения выделять в предусмотренные модули и объекты; не смешивать ее с общим алгоритмом без точки переопределения.
- На сервере для прикладного текущего времени использовать `ТекущаяДатаСеанса()`, а не время серверного компьютера `ТекущаяДата()`. Для независимой от часового пояса отметки выбирать универсальное время; явно различать эти назначения.
- Разрядность денежных полей проектировать с учетом поддерживаемых валют и стран; использовать предусмотренные определяемые типы и правила № 778, а не повсеместно фиксированную малую разрядность.

## 20. Регламентные задания, библиотеки и обновления

**Источники:** № 540, с. 92–93; № 402, с. 94; № 539, с. 95–96; № 760, с. 97–99; № 551–554, с. 292–300; № 739, с. 301; № 644, с. 302–307; № 668, с. 308; № 690, с. 309–316; № 706, с. 44–45; № 534, с. 74–75.

### Фоновые и регламентные задания

- Логика должна выполняться без формы, интерактивных вопросов и зависимости от клиентских переменных.
- Предусматривать диагностику, настройку расписания и ручной запуск там, где это определено стандартом. При БСП использовать ее рабочее место управления заданиями.
- Учитывать конкурентное выполнение, блокировки и доступные права. В сервисной модели соблюдать специальные ограничения очередей и запуска № 760.

### Библиотеки и совместимость

- Разделять публичный API, API для определенных потребителей и внутреннюю реализацию. Потребителям не опираться на служебные детали библиотеки.
- Поставляемые и переопределяемые объекты различать по правилам библиотеки. Не менять поставляемый объект как обычную точку настройки.
- Переопределяемые общие модули предназначены для вызова из библиотеки. Не строить на их служебных процедурах собственный публичный API потребителя.
- Обеспечивать обратную совместимость в пределах подредакции библиотеки. Изменение третьей или четвертой цифры версии не дает общего разрешения ломать API; исключения LTS учитывать по № 644.
- При замене экспортного метода сохранять совместимый устаревший вход и документировать замену до предусмотренного удаления.
- Не переименовывать общий модуль с последующим созданием нового под прежним именем. Другие переименования проверять на влияние на настройки, роли, внешние обращения и обновления.
- Устаревшие метаданные выводить из использования поэтапно, с переносом данных, корректировкой ссылок и обработчиками обновления. Не удалять их сразу из поставляемой конфигурации.

### Обновление данных

- При изменении структуры и смысла данных проектировать переход существующей базы, а не только создание новой.
- При БСП использовать подсистему обновления версии ИБ: регистрацию обработчиков, версии, зависимости и режимы `Монопольно`, `Оперативно`, `Отложенно` согласно № 690.
- Обработчики должны поддерживать предусмотренное повторное выполнение и возобновление после прерывания, не требовать ручного исправления каждого объекта пользователем.
- Большие обновления выполнять порциями; поддерживать корректность данных в период отложенной обработки и проверять ответственные чтения.
- Для выпуска учитывать нумерацию версий, описание релиза, дистрибутивы и проверку конфигурации: № 483, с. 50; № 482, с. 51; № 731, с. 46–47.
