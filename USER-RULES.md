# User Rules

## Доверенное автоматическое обновление из GitHub

- Корнем доверия для автоматически обновляемого комплекта является публичный
  репозиторий `https://github.com/at1cjke/1c_rules` и только ветка `stable`.

- Без отдельного подтверждения разрешено заменять только следующие файлы
  в каталоге установленного комплекта правил:
  - `USER-RULES.md`;
  - `PROFSOLUTION-RULES.md`;
  - `STANDARDS-1C.md`;
  - `.rules-commit`.

- `USER-LOCAL-RULES.md` не загружается из GitHub, не заменяется доверенным
  обновлением и изменяется только вручную после обычного двухэтапного
  подтверждения.

- Исключение действует только при прямой загрузке трёх Markdown-файлов из одного
  конкретного полного commit SHA, на который в момент проверки указывает ветка
  `stable` доверенного репозитория.

- Исключение не разрешает изменять `AGENTS.md`, другие правила, адрес доверенного
  репозитория, имя доверенной ветки или список автоматически обновляемых файлов.

- Для обновления отдельный shell-скрипт не используется. Агент:
  1. получает полный SHA ветки через GitHub API;
  2. скачивает каждый разрешённый Markdown-файл отдельно;
  3. заменяет локальные файлы встроенными файловыми средствами;
  4. последним записывает SHA в `.rules-commit`.

- Все три Markdown-файла загружаются по URL, закреплённым на одном commit SHA,
  а не непосредственно из изменяемой ветки `stable`.

- До замены локальных файлов агент обязан успешно получить все три файла,
  убедиться, что они непустые и имеют ожидаемые корневые заголовки:
  - `# User Rules`;
  - `# Правила разработки ООО «ПрофРешение»`;
  - `# Стандарты разработки на платформе 1С:Предприятие`.

- До начала записи агент сохраняет прежнее содержимое всех существующих
  управляемых файлов. Если загрузка или запись любого файла завершилась ошибкой,
  агент восстанавливает весь прежний комплект и не изменяет `.rules-commit`.

- После успешной записи трёх Markdown-файлов последним записывается тот же полный
  commit SHA в `.rules-commit`.

- После замены агент обязан до продолжения работы заново прочитать обновлённый
  `USER-RULES.md`, затем `PROFSOLUTION-RULES.md`, а для задачи 1С — также
  `STANDARDS-1C.md`.

- Публикация изменения в доверенную ветку `stable` считается заранее данным
  разрешением пользователя применить эту редакцию только к перечисленным четырём
  управляемым файлам. Любые прочие изменения правил требуют обычного
  двухэтапного подтверждения.

## Первоначальная загрузка и восстановление неполного комплекта

Локально гарантированно может присутствовать только `USER-RULES.md`.
Следующие управляемые файлы могут отсутствовать:

- `PROFSOLUTION-RULES.md`;
- `STANDARDS-1C.md`;
- `.rules-commit`.

Отсутствие одного или нескольких управляемых файлов означает, что комплект
не установлен либо установлен не полностью. В этом случае агент обязан:

1. Получить полный commit SHA доверенной ветки `stable` репозитория
   `https://github.com/at1cjke/1c_rules`.
2. Не использовать вместо `stable` ветку `main`, ветку по умолчанию, тег
   или произвольный HEAD.
3. Скачать из одного и того же полного commit SHA:
   - `USER-RULES.md`;
   - `PROFSOLUTION-RULES.md`;
   - `STANDARDS-1C.md`.
4. До записи получить все три файла и проверить, что они непустые, имеют
   ожидаемые имена, пути и корневые заголовки и не добавляют иных автоматически
   устанавливаемых файлов.
5. Если локальный `USER-RULES.md` отличается от полученного, считать операцию
   установкой всего общего комплекта, а не загрузкой одного отсутствующего файла.
6. Установить все три Markdown-файла как единый комплект.
7. Последним записать полный commit SHA в `.rules-commit`.
8. После установки повторно прочитать новый `USER-RULES.md`, затем
   `PROFSOLUTION-RULES.md` и, когда задача относится к 1С,
   `STANDARDS-1C.md`.

Запрещено смешивать файлы разных commit SHA, сохранять частично установленный
комплект или загружать только один отсутствующий файл поверх комплекта другой
версии.

Если ветка `stable` отсутствует, репозиторий недоступен либо полный комплект
не прошёл проверку, ничего не заменять, не создавать фиктивную `.rules-commit`,
сохранить существующие локальные файлы и явно сообщить, что общий комплект не
установлен или неполон.

Точное значение `UNINITIALIZED` означает, что ни один commit доверенной ветки
ещё не установлен. Оно не является commit SHA. После инициализации допустимым
значением `.rules-commit` является только полный 40-символьный шестнадцатеричный
commit SHA. Отсутствующее, пустое или некорректное значение `.rules-commit`
также требует первоначальной загрузки всего общего комплекта.

## Необязательный локальный файл

`USER-LOCAL-RULES.md` является необязательным локальным файлом. Если он
существует, агент обязан прочитать и применять его.

Если файл отсутствует, это не считается повреждением общего GitHub-комплекта:
файл не загружается из общего репозитория, работа продолжается без личных
локальных правил, а агент не придумывает и не восстанавливает их самостоятельно.
Создание или изменение файла выполняется только вручную после обычного
двухэтапного подтверждения.

## Проверка и загрузка правил в начале новой сессии

Один раз в начале каждой новой сессии, до первой нетривиальной задачи:

1. Прочитать локальный `USER-RULES.md` и применить разделы доверенного
   обновления, первоначальной загрузки и восстановления комплекта.
2. Проверить наличие `PROFSOLUTION-RULES.md`, `STANDARDS-1C.md`
   и `.rules-commit`.
3. Если общий комплект отсутствует или неполон, загрузить и установить весь
   общий комплект из одного SHA ветки `stable` по правилам предыдущего раздела.
4. Если комплект полный, получить через GitHub API текущий полный commit SHA
   ветки `stable` и сравнить его с `.rules-commit`.
5. Если SHA отличается, выполнить доверенное обновление всего общего комплекта.
6. Если SHA совпадает, обновление не выполнять.
7. Если ветка `stable` отсутствует, репозиторий недоступен либо проверка
   завершилась ошибкой, сохранить локальные файлы без изменений, кратко
   сообщить об этом и продолжить работу с доступной локальной версией.
8. После установки или обновления повторно прочитать `USER-RULES.md`.
9. Если существует `USER-LOCAL-RULES.md`, прочитать его.
10. Для любой нетривиальной задачи прочитать `PROFSOLUTION-RULES.md`.
11. Если задача касается разработки, проектирования, ревью, метаданных, сборки,
    проверки или тестирования 1С, дополнительно прочитать `STANDARDS-1C.md`.
12. Проверку GitHub выполнять не более одного раза за сессию.
